Step 01 — Terima Requirement dari PM
PRD diterima dari Product Manager, lalu dianalisa untuk memahami seluruh scope fitur, business rules, dan batasan setiap role. Proses ini menjadi fondasi seluruh aktivitas testing di sprint tersebut.
  • Baca PRD secara menyeluruh — identifikasi ambiguitas dan minta klarifikasi ke PM
  • Petakan fitur ke role masing-masing (siapa yang boleh akses apa)
  • Tandai area berisiko tinggi yang butuh perhatian lebih saat testing
Step 02 — Analisa Flow & Buat Acceptance Criteria
Setelah PRD dipahami, langkah berikutnya adalah membuat Acceptance Criteria per fitur dan membuat Business Flow visual di Figma untuk tiap role. RBAC matrix juga disusun di sini.
  • Tulis Acceptance Criteria — kondisi yang harus terpenuhi agar fitur dianggap done
  • Buat Business Flow diagram per role di Figma (Admin, Supervisor, Agent, Sales, dst.)
  • Susun RBAC matrix — permission apa saja yang dimiliki tiap role
  • Review bersama developer dan PM sebelum testing dimulai
Step 03 — Buat Test Case
Test case disusun berdasarkan AC dan business flow yang sudah dibuat. Mencakup positive case, negative case, boundary case, dan RBAC testing untuk setiap role.
  • Positive test case — alur happy path sesuai requirement
  • Negative test case — input invalid, edge case, dan error handling
  • RBAC test case — verifikasi permission tiap role sesuai PRD
  • API test case — validasi request/response menggunakan Postman
  • DB validation checklist — data apa yang harus dicek di MongoDB
Step 04 — Testing di Development Environment
Eksekusi test case di dev environment. Menggunakan multi-device (Web browser + scrcpy untuk Android) dan multi-role login secara bergantian untuk mengcover semua skenario.
  • Web testing — Chrome/browser dengan berbagai role login (Admin, SPV, Sales)
  • Mobile testing — via scrcpy untuk Android, semua 5 role (Admin, Supervisor, SPV Sales, Agent, Sales)
  • API testing via Postman — validasi response, status code, dan payload data
  • DB validation via MongoDB Compass — cek konsistensi data antara UI dan database
Step 05 — Report Bug
Setiap bug yang ditemukan didokumentasikan lengkap dengan steps to reproduce, expected vs actual result, severity, priority, dan evidence (screenshot/video via Jam.dev atau BetterBugs).
  • Buat bug report di OpenProject dengan template standar
  • Lampirkan evidence — screenshot atau screen recording via Jam.dev/BetterBugs
  • Tentukan severity (Blocking/Critical/Major/Minor) dan priority (High/Medium/Low)
  • Tag developer yang bertanggung jawab dan set sprint target fix
  • Untuk bug DB — sertakan MongoDB query result sebagai bukti inkonsistensi
Step 06 — Testing di Production Environment
Setelah dev environment clear, testing dilanjutkan di environment staging/production untuk memvalidasi bahwa fitur berjalan dengan benar di kondisi nyata.
  • Jalankan ulang test case kritis di staging environment
  • Validasi data production — pastikan tidak ada data corruption
  • Test integrasi dengan channel eksternal (WhatsApp, dll.) di production
  • Smoke test — cek fitur utama berjalan normal setelah deployment
Step 07 — Update Tiket & Retest Bug Fix
Setelah developer melakukan fix, tiket diupdate dan retest dilakukan untuk memverifikasi bahwa bug sudah terselesaikan dan tidak ada regression issue yang muncul.
  • Update status tiket di OpenProject setelah developer marking "Fixed"
  • Retest bug sesuai steps to reproduce yang sudah didokumentasikan
  • Jika bug masih ada → reopen tiket dengan evidence baru
  • Jika fix valid → tutup tiket dan tandai "Verified"
  • Quick regression check pada modul yang terdampak oleh fix
Step 08 — Regression Testing & UAT
Tahap akhir sebelum release. Regression testing memastikan fitur lama tidak terdampak oleh perubahan baru. UAT adalah sign-off akhir bahwa produk siap ke production.
  • Full regression testing — semua fitur di-test ulang, bukan hanya yang baru
  • Cross-platform regression — Web dan Mobile ditest bersamaan
  • Multi-role regression — semua role diverifikasi tidak ada permission yang berubah
  • UAT documentation — hasil testing didokumentasikan sebagai sign-off release
  • Go/No-Go decision bersama PM dan tim sebelum push ke production
